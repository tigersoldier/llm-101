# 2.6 接入模型、回归测试与交接

- 状态：待写

## 目标

- 知道模型侧只改 `GPTConfig.vocab_size`；`TinyGPT.forward`、注意力、block、LayerNorm 的代码都不变。
- 能算出词表变化带来的参数量变化：`5,824 + (V - 68) × 16`，并用 $V=512$ 得到 12,928。
- 能用新 tokenizer 的 ids 跑通 `TinyGPT` 前向，得到形状为 `[1, T, V]` 的 logits，并用 argmax + 词表查出片段；知道输出是随机权重的噪声。
- 理解固定 id logits 回归：固定旧 `GPTConfig`、seed 和手写 id，比较第 1 章与第 2 章的 logits，证明模型代码没变；不用“同一文本的新旧 id”做等价。
- 知道 tokenizer 与模型的 `vocab_size` 必须一致；越界 id 会由 `Embedding` 抛出 `IndexError`。
- 跑完整章验收，写清第 3 章的入口与不变项。

## 内容安排

1. 问题：tokenizer 换了，模型要不要改？答案：只改 `vocab_size`。列出不变项：`Embedding` 的查表逻辑、位置嵌入、2 层 block、最终 LayerNorm、共享输出、`forward` 的 `[B, T] → [B, T, V]`；只变两项：token 嵌入表的行数、输出 logits 的最后一维。
2. 参数量：用 1.8 的 5,824 作基线，token 嵌入从 $68 \times 16 = 1{,}088$ 变成 $512 \times 16 = 8{,}192$，增加 7,104；位置嵌入 256、两个 block 4,448、最终 LayerNorm 32 都不变；总计 $8{,}192 + 256 + 4{,}448 + 32 = 12{,}928$。给公式 `5,824 + (V - 68) × 16`，并说明实际 $V$ 以 2.3 的语料为准。
3. 配置与前向：`GPTConfig` 的六个字段；`vocab_size=tokenizer.vocab_size`，其余 `d_model=16`、`n_layers=2`、`n_heads=2`、`d_ff=32`、`max_seq_len=16`。用固定 seed 构造 `TinyGPT`；英文/中文固定样例的 ids → `[1, T]` → logits `[1, T, V]`；取最后一个位置 argmax，用 `vocabulary[argmax]` 查出 token；说明这是噪声，不是生成。
4. 参数与形状的实际结果：打印 `logits.shape`、`T`、`V`、`argmax`、`vocabulary[argmax]`；两条样例各一行；`T` 远小于 16，说明 BPE 把 2.1 的超限问题解决了多少（只针对这两条样例，不外推）。
5. 回归测试：固定旧配置 `GPTConfig(vocab_size=68, d_model=16, n_layers=2, n_heads=2, d_ff=32, max_seq_len=16)`、`generator=manual_seed(7)`、手写 ids `[5, 12, 3, 9]`；从 `ch01/end` 生成 logits 存到 `tests/data/ch01-logits.json`；`tests/test_regression.py` 用 `torch.testing.assert_close(..., atol=1e-6, rtol=0)` 比较。解释为什么不能用新文本 id：词表从 68 变到 512，同一个词的 id 不同，形状也不同；回归要证明的是“模型代码没动”，所以固定旧形状和手写 id。
6. 一致性检查：`config.vocab_size == tokenizer.vocab_size`；所有输入 id 小于 `vocab_size`；越界 id 由 `Embedding` 抛 `IndexError`（第 1 章已有行为，不新增检查）；`bos_id`/`eos_id` 在新词表中仍指向正确 token。
7. 完整管线 stage 6：英文/中文固定样例 → tokenizer 编码 → `TinyGPT` → logits → argmax → `vocabulary` 查 token；`show_tokenizer.py --stage 6` 的实际输出；保存/加载 tokenizer 后再跑一次，结果一致。
8. 全章验收：`cd ch02/end && uv run pytest -q`（记录实际通过数）；根目录 `uv run pytest -q`；`uv run mkdocs build --strict`；`ch01/end` 的 39 个测试仍通过；`show_tokenizer.py --stage 1` 到 `--stage 6` 都能跑。
9. 交接：第 3 章在 `ch02/end` 上加 `Parameter`、各层 `backward`、softmax 交叉熵和 next-token 目标；tokenizer 与 `samples/` 冻结；第 7 章才换真实语料和 8192 词表；`<pad>` 等到真正需要 padding 时再加。
10. 图：`15-tokenizer-model.svg`（文本 → tokenizer → ids → 简化模型栈 → logits → argmax → token；完整架构见 1.8）、`16-regression.svg`（旧配置手写 id 的回归路径与新词表前向路径并列，标出哪些代码变、哪些不变）。

## 写作注意

- 不重讲 1.8 的 `TinyGPT` 结构；只引用形状和参数量，明确“哪些不变、哪些变”。如果读者需要回顾，给一句指针并复述最小定义。
- 回归测试必须用旧配置和手写 id；不要用新 tokenizer 编码后的文本 id 做等价。词表变了，id 和形状都变了，那条路证明不了模型代码没变。
- 新词表下的模型输出是随机权重的噪声；不要把它写成“模型会说话了”，也不要展示成生成样例。
- 不训练、不反向传播、不引入优化器；第 3 章才讲梯度。2.6 是收束节，不再引入新的 tokenizer 机制。
- 参数量用 $V=512$ 举例，但要写明实际值以 2.3 的语料为准；如果实际 $V$ 不是 512，正文同时给公式和实际数字。
- `tests/data/ch01-logits.json` 是从 `ch01/end` 生成的只读 golden 文件，不要用 `final/` 或新模型重新生成；生成命令和来源写在测试文件或 README 里。golden 文件记录生成时的 Python/torch 版本；CI 使用仓库的 `uv.lock`；升级 torch 后如果出现浮点差异，先确认模型代码没变，再单独更新 golden 并在提交说明里记录。
- `ch01/end` 是冻结快照，本章不改它；如果 golden 对不上，先查是否误改了模型代码或 seed。
- 本节不写“数学补充”：参数量加法和形状检查不需要大学数学。
