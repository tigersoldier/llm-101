# 2.4 编码与解码：接口与未知字符

- 状态：待写
- 预计篇幅：约 3800 字，代码 5 处，图 4 张
- 前置：2.3

## 目标

- 能写出 `encode`：码点 → 初始符号或未知哨兵 → 按 rank 重放合并 → 映射 id → 可选 `<bos>`/`<eos>`。
- 能写出 `decode`：id → 词表 token → 拼接；默认跳过特殊 token，`skip_special_tokens=False` 时保留。
- 理解未知码点为什么映射成一个 `<unk>`，以及为什么它不能与相邻符号合并。
- 知道文本往返的条件：所有码点都在训练字母表内；未知码点会丢失（与第 1 章行为一致）。
- 能保存/加载 JSON，并保证保存前后词表与编码结果一致。
- 知道五个接口的行为与第 1 章一致；`encode`/`decode` 的签名与关键字参数不变。

## 内容安排

1. 问题：2.3 的词表有 id，但还没有“文本 → id → 文本”的函数；编码不是重新训练，而是按已学到的合并顺序重放。
2. `encode` 的编号步骤：
   1. 逐码点查初始 token 表；在表里的保留，不在表里的替换成哨兵 `"\0"`；
   2. 按合并 rank 从小到大，对整条符号序列调用 2.2 的 `merge_pair`；
   3. 把每个符号映射成 id；哨兵映射成 `unk_id`；
   4. 需要时在开头插入 `bos_id`、结尾插入 `eos_id`。
   给出 `vocab_size=12` 的迷你 tokenizer 上的完整 trace：`"lower"` → `["l","o","w","e","r"]` → rank 0 → `["lo","w","e","r"]` → rank 1 → `["low","e","r"]` → `[1, 11, 3, 6, 2]`。
3. 为什么要哨兵：如果未知字符直接变成字符串 `<unk>`，它可能和相邻字符合并成一个不存在的 token；用一个不在初始字母表、也不在合并表里的符号阻断合并。给 `["a","\0","b"]` 与 `["a","b"]` 的对比；说明 `count_pairs`/`learn_merges` 从不会产生含哨兵的合并。
4. `decode` 的编号步骤：逐 id 校验范围 → 取词表 token → 特殊 token 处理 → 拼接。`skip_special_tokens=True` 默认跳过 `<unk>`、`<bos>`、`<eos>`；`False` 时原样输出 `<unk>`/`<bos>`/`<eos>`。给 `[1, 11, 3, 6, 2]` → `"lower"` 与 `"<bos>lower<eos>"` 两个结果。
5. 未知字符：用迷你 tokenizer 编码 `"lowx"` → `[1, 11, 0, 2]`；`decode` → `"low"`；`decode(..., skip_special_tokens=False)` → `"<bos>low<unk><eos>"`。用全量 tokenizer 编码含生僻字的留出句，数 `<unk>`；把“有损往返”写成一条明确契约。
6. 边界：`decode` 对越界 id 报 `ValueError`；`encode` 对输入中的 NUL 报 `ValueError`（哨兵是保留符号）；空文本 `encode("")` 返回空列表或只有 BOS/EOS，按签名说明。文本中包含 `<bos>` 这类拼写时按普通码点处理，不注入特殊 token；特殊 token 只由 `add_bos`/`add_eos` 控制。
7. 保存/加载：`save(path)` 写 UTF-8 JSON，字段为 `format_version`、`special_tokens`、`initial_tokens`、`merges`；`load(path)` 校验版本、重建对象。说明只保存“原料”，不保存派生词表，避免文件与代码不一致。给保存后再加载、`vocabulary` 与 `encode("lower")` 完全一致的例子。
8. 参考实现：`encode`、`decode`、`save`、`load` 的用法、输入输出、样例、带注释的签名和参考实现；`_merge_by_rank` 作为内部辅助函数说明，但不要求读者记住名字。
9. 接口契约：五个成员与第 1 章一致；`BPETokenizer.train` 与 `load` 是新增入口；`CharacterTokenizer` 被替换，不再保留；`bos_id`/`eos_id` 的数值变了但含义不变。
10. 图：`08-encode-decode.svg`（文本 → 符号 → 重放合并 → id → 解码）、`09-unknown.svg`（哨兵阻断合并与 `<unk>` 往返）、`10-save-load.svg`（JSON 原料与重建词表）。
11. 扩展阅读：Unicode 码点、UTF-8 字节、字节级 BPE 与码点级 BPE 的差别；为什么 GPT 系列用字节级、本章为什么用码点级；中文与 emoji 在两种切分下的具体例子；`11-unicode.svg`。

## 写作注意

- `encode`/`decode` 是第 1 章已有的五个成员，签名与 `add_bos`/`add_eos`/`skip_special_tokens` 关键字不变；构造、训练、加载接口可以不同，但 `train`/`save`/`load` 要写清。
- 不在 2.4 重讲合并算法；只引用 2.2 的 `merge_pair` 和 2.3 的合并顺序。`_merge_by_rank` 的朴素实现按 rank 依次调用 `merge_pair` 即可，不引入堆优化。
- 未知字符行为与第 1 章一致：一个未知码点一个 `<unk>`；`decode` 默认跳过特殊 token，所以往返会丢失未知字符。不要改成 U+FFFD，也不要把 `<unk>` 从 `skip_special_tokens` 中排除；这是本章的明确契约。
- 特殊 token 只由 `add_bos`/`add_eos` 控制；输入文本里的 `<bos>` 按普通码点处理，不注入特殊 token。不要在这里引入“输入含特殊 token 拼写就报错”的新规则。
- `save` 用普通 UTF-8 JSON，不引入 pickle、压缩包或二进制格式；只保存 `special_tokens`、`initial_tokens`、`merges` 和 `format_version`，词表由 `load` 重建。
- 迷你 tokenizer（12 个 token）只用于手算；全量 tokenizer（目标 512）用于固定样例与报告。正文要明确当前例子用的是哪一个，避免数字对不上。
- 扩展阅读讲 Unicode 与字节级 BPE 的边界：中文一个字是一个码点、UTF-8 下通常是 3 个字节；emoji 可能是一个码点、4 个字节；字节级 BPE 会把字节序列当符号。不要把字节级实现写进正文。
- 本节不写“数学补充”：编码步骤和 id 映射不需要大学数学。
